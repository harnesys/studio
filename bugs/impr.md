## Реальные баги, пойманные в прогоне

1. **`plan_item_update` не нашёл валидный id сразу после перезаписи плана.** Я сделал `plan_save` (раунд 2), потом update на id `b1540877-...` — ошибка `not found`, при том что **тот же самый id был в списке «Valid ids» в этой же ошибке** (пункт `3:b1540877-...`). Повтор того же вызова позже прошёл успешно. Похоже на stale-индекс/гонку после перезаписи плана в том же ране. Починить бы.
2. **`plan_save` не возвращает id пунктов.** Я могу обновлять статусы только потому, что id приходят через инъекцию `<active-plan>` или из текста ошибки. Если инъекция пропадёт (компакция, длинный тред) — тупик. `plan_save` должен возвращать `{items: [{id, title}]}`.
3. **Утечка «Continue» в видимый текст при handoff.** Реплика Handoff Demo оборвалась артефактом: «даже при желанииContinue я бы демо не продолжил». Внутренний токен попал в пользовательский текст. Это видно в ленте владельцу, выглядит как глитч рендера или сборки стрим-чанков.

## Непредсказуемое по дизайну

4. **`map` не принимает инструкцию обработки.** Я передал `["red","green","blue"]` — и тело карты решает само, что с этим делать. Итог: один элемент эхом вернул `"red"`, другой выдал эссе на 66 токенов про цвет, третий эхом `"blue"`. Расход токенов на элемент не контролируется вообще. Нужен параметр `instruction` (шаблон с `$item`/`$index`) и, в идеале, `maxTokens` на элемент.
5. **`agents_spawn` возвращает reasoning-трейсы детей.** В Spawn results притащился полный `reasoning` + `usage` JSON каждого ребёнка. Хуже того: у Echo в reasoning рассуждения про «You are an expert software engineer» и «deferred-tools reminder», хотя это делегат echo-bot без инструментов (packs: core). Делегаты наследуют общий scaffold, несмотря на узкую роль. Предлагаю: по умолчанию отдавать только `content`, reasoning/usage под флагом, и для безынструментных детей вырезать каталог deferred-инструментов из контекста.
6. **Бюджетный счётчик скачет без объяснений.** Было `385/400`, стала новая реплика юзера — `397/400`. Это per-run счётчик, сбрасывается на каждом ходе графа от нового сообщения, но подпись об этом молчит. Одна строка `per run; resets on new user message` снимает ненужную тревогу «бюджет восстанавливается?».

## Эргономика инструкций для меня

7. **Разрешения: текст описывает режим, в котором я не работаю.** Системный промпт говорит «write_file, shell, fetch gated and the user is asked per call», но за 2 раунда ни один вызов не требовал одобрения (режим auto). Я честно писал «причину перед вызовом» в театральном стиле. Добавь в промпт активный permission mode, и я перестану репетировать одобрения, когда их нет.
8. **Конфликт хук vs промпт на мелких задачах.** «Invoke relevant skill BEFORE ANY response» против «answer questions within the loop». На демо-ходках это чистый оверхед; сформулируй порог: скиллы для нетривиальной работы, эхо-команды без ритуала.
9. **Описание `agents_create` перепутано фрагментами**: «...when budget is omitted. skills/mcpServers/packs/enabledPlugins: sources...» — склейка шаблона не в том порядке, первое прочтение сбивает.
10. **`memory_write` не чинится по id.** Чтобы исправить свою запись (я допустил опечатку с CJK-иероглифом в тексте), пришлось delete + re-write, потому что key я не передал. Либо обязательный `key` для long-scope, либо патч по id.
11. **`plan_item_update` просит полный UUID**, хотя ошибка сама показывает индексы `0..6`. Принимать индекс или префикс id (как агенты принимают 8-символьный prefix) — заметно дешевле по токенам на каждый статус.
12. Мелочь: дубль `Skill`/`load_skill`. Оставить одну ручку.

## Приоритет правок, как я бы расставлял

1. `map` + `instruction` (без этого инструмент непредсказуем по стоимости).
2. Гонка plan-индексов после перезаписи (реальный баг с воспроизведением в этом треде).
3. Утечка `Continue` в handoff-текст.
4. Spawn results: content by default, reasoning за флагом.
5. `plan_save` возвращает id; update принимает индекс/префикс.
6. Подпись per-run у бюджета; активный permission mode в промпте.

Инструкций в целом достаточно для принятия решений: развилки spawn-vs-handoff, план-vs-текст, память-vs-recall покрыты явно. Не хватает именно данных окружения (режим разрешений, смысл счётчиков) и управляемости `map`.

Не проверял и оставляю за скобками: создание schedule/webhook (не хотел плодить живые крон-задачи в демо — тест threadId="self" отдельно), компакцию на длинном треде, пересечение permissions-карты у делегата с `allow`.
