# Ревью флоу: сообщение пользователя → финальный ответ агента

## 1. Архитектурная оценка (общая картина)

Сама слоистая структура хорошая: hexagonal в движке (`ports/adapters/application/domain`), use-cases в studio, единый `SessionEvent` как контракт, snapshot/event-sourcing в SQLite. Клиентский FSD тоже разумный. Но на стыках слоев есть **системная проблема: ни один участник конвейера не владеет правдой о состоянии рана** — движок, реестр активных ранов, серверный дрейнер и клиентский store каждый держит свою частичную модель, и они расходятся. Все критичные баги ниже — следствие именно этого.

Конвейер: `send → RunEngine (graph loop) → engine replay log → drainAgentRun → ActiveRunRegistry (buffer + listeners) → SSE → client store`, и параллельно всё пишется в SQLite через `commit()`. Четыре копии событий — это уже само по себе риск рассинхронизации, и он реализовался.

## 2. Критичные баги (P0) — корневые причины симптомов

### Баг 1. ReAct-граф невозобновляем: `$output.toolCalls` теряется при resume

Это корень «ask_user не хочет нормально работать».

- `graph.ts:206` — `let output: unknown = null;` — **транзиентная локальная переменная**, в снапшот не пишется (`mkSnap` в `graph-snap.ts:18` сохраняет только `state/cursor/budget`).
- Прерывание `ask_user` происходит внутри узла `act`; `cursor.interrupt.nodeId = 'act'`. При resume движок стартует сегмент с `startNodeId='act'` (`run-engine.ts:331`).
- Узел `act` — batch `calls: '$output.toolCalls'` (`react-preset.ts:13`). `executeToolCall` делает `evalExpr(batch.calls, slots)` (`tool-call.ts:127`), где `slots.output = ctx.output ?? null` = `{}` → `unknown_path` → исключение → `runSegment` ловит → `status='failed'`, `run.failed`.
- Т.е. **resume для ReAct в принципе не может пройти через узел act** — до пользователя ответ не дойдет никогда: после respond ран умирает с `run.failed`. Побочно: `ask_user` внутри параллельного батча (`Promise.all` воркеров) бросает `AskUserInterrupt`, теряя результаты уже выполненных вызовов, а при resume весь батч выполняется заново → двойные side effects.

Нужен один из вариантов: (а) персистить `output`/последний `LlmResult` в снапшоте и восстанавливать; (б) при resume с `tool:call`-узла восстанавливать `output` из последнего assistant-сообщения в `$state.messages` (там уже лежит `toolCalls`, `finishReason` — `graph.ts:563-572`).

### Баг 2. Гонка `recover()` vs respond: команда навсегда застревает в очереди

Это точное объяснение Bug Report 1 («сервер проглатывает respond, событий нет»).

- `session.ts:114` — `void engine.recover()` — **не awaited**. `createRun` возвращается сразу, `resume-thread-run.use-case.ts:114` синхронно регистрирует ран в `activeRuns`, т.е. `POST /runs/:id/respond` может прийти, когда `recover()` ещё в полёте (`state.load()` — асинхронный I/O).
- В этот момент `engine.status === 'running'` (дефолт). `command()` кладет resume в очередь, `drainQueue()` (`run-engine.ts:351`) видит `status === 'running'` и не-cancel команду → `break`.
- Когда `recover()` завершается и ставит `status='needs_input'`, **никто не вызывает `drainQueue()` повторно**. Команда лежит в очереди вечно: HTTP-запрос висит, событий нет, статус `needs_input`. Клиент ретраит через ~15с — и всё повторяется.

Фикс: `await engine.recover()` в `createRun` (или в конце `recover()` вызывать `void this.drainQueue()`), плюс в `recover()` возвращать промис, который студия дожидается до `activeRuns.register`.

### Баг 3. Шторм `POST /resume` (60 запросов за 4с в логах)

Цепочка бесконечного цикла на клиенте:

1. `hitl-prompt.tsx:27-31`: `useEffect` — `pending && !streaming` → `resumePausedThread(thread.id)`. Срабатывает после перезагрузки страницы, когда в БД есть незакрытый `ask`, а in-memory активных ранов у клиента нет.
2. `resume-paused.ts:23-30`: `resumeThread` падает → `catch` → `store.finishRun(threadId)` → `streaming=false` → зависимости эффекта изменились → **эффект срабатывает снова** → бесконечный цикл.
3. Сервер на каждый запрос отвечает **409**: `resume-thread-run.use-case.ts:69` — `findByThread` находит «живой» ран. А он действительно числится живым, потому что `drainAgentRun` (`drain-agent-run.ts:16`) висит в `for await (run.stream())` — поток движка **не закрывается при `needs_input`** (закрытие только на terminal-статусе, `run-engine.ts:379`), значит `finish()` не вызывается, запись в реестре не удаляется. Плюс отдельное окно: после `finish()` запись держится ещё 30с (`active-runs.adapter.ts:90-92`), и `findByThread` её тоже находит → 409 даже для честно завершенного рана.

Итого: `/resume` неидемпотентен, а клиент не различает «ран уже припаркован» от «рана нет». Фиксы: (а) на клиенте — не ретраить в эффекте автоматически/ретраить с backoff и выходом по 409 (409 = ран уже жив, нужно просто подключиться к его SSE, а не спамить); (б) на сервере — `findByThread` должен игнорировать `finished` записи; (в) `POST /resume` при существующем живом ране должен возвращать **его runId 202**, а не 409 — тогда клиент подключается к стриму и цикл разрывается.

### Баг 4. Молчаливые no-op в движке — «сервер проглатывает запросы»

- `run-engine.ts:283` — `if (!this.interrupt || interruptId !== cmd.interruptId) return;` — respond/reject с чужим/устаревшим askId завершается **успехом без единого события**. HTTP 200 `{ok:true}`, клиент уверен, что ответ принят.
- `run-engine.ts:355-357` — команды на терминальном ране молча `resolve()`.
- Дедупликация `applied` (строка 276) при повторном том же payload тоже молчит.

Все три пути должны возвращать явную ошибку (в studio это превратится в 400/409, и клиент покажет toast вместо «зависания»).

## 3. Существенные баги (P1)

1. **`pendingHitl` не очищается на `resumed`** (`pending-hitl.ts:11-25`): сброс только на `done`/`error`. После успешного respond форма ответа висит до конца рана (пока не придет следующая модель-дельта... а не придет nothing до `think`, т.е. висит секунды/десятки секунд). Событие `resumed` уже есть в `SessionEvent` (`ports/session.ts:44`) и эмится движком (`run-engine.ts:330`) — клиент его просто игнорирует.
2. **Orphan tool_use при reject**: reject ask_user → `startNodeId='act'`, `rejected=true` → узел act пропускается **без записи tool-сообщения** (`isSkippedEntry`, `graph-edges.ts:23`). При этом в `$state.messages` уже лежит assistant-сообщение с tool-calls. На следующем витке `think` уходит история с `tool-call` без парного `tool-result` → большинство провайдеров отвечают 400. Нужен синтетический tool-result «rejected by user» (механизм уже есть в `tool-call.ts:354-366` для approve-ветки, но не для skip-entry).
3. **Дублирование событий `ask` при recover**: `recover()` (`run-engine.ts:168`) реэмитит `ask` в replay-лог, но тот же `ask` уже лежит в БД и приедет клиенту через `getThread` reconcile → дубликаты в `events[]`.
4. **Permission gate 'ask' не работает как HITL**: `checkPermission` с gate `ask` возвращает tool-result «permission ask: …» с `isError` (`tool-call.ts:212-227`) — модель видит строку-ошибку и продолжает, вместо прерывания для подтверждения человеком. Т.е. режим `mode='ask'` из `tool-confirm-policy.ts` для shell/http фактически не задействует HITL-пайплайн (source 'permission' в `SessionEvent` мертвый код).
5. **Replay-буфер движка растет безгранично** (`run-engine-stream.ts:21`): на длинных чатах каждый ран держит все события в памяти; буфер в `ActiveRunRegistry` тоже (`active-runs.adapter.ts:124`) и чистится только через 30с.
6. **Нет GC для parked runs**: ран в `needs_input` живет вечно — ни таймаута, ни автокансела, ни лимита на количество припаркованных ранов на воркспейс.
7. **`tokens += 1` при отсутствии usage** (`graph.ts:581-584`) и мертвый код fallback-цикла (`graph.ts:538-539` — пустой `if`, повторный стрим после частичных дельт на фейле не откатывается).

## 4. Мелкие (P2)

- Дубликат `user`-события: оптимистичный локальный + replay с сервера. Дедуп в `session.store.ts:60-66` работает только если событие **последнее** в списке — после reconcile `replaceEvents` порядок другой, возможны визуальные дубли.
- `finishRun` в `drain-run-stream.ts:45` зовется в `finally` даже когда SSE умер по сети при живом ране — клиент считает ран мертвым, сервер живым → рассинхрон, знакомый по багу 3.
- `resolveConcurrency` дублирует проверку `'parallel' | 'sequential'` (строки 71-73 и 84-87 в `tool-call.ts`).
- `get-thread.use-case.ts` перечитывает **всю** историю событий потока на каждый `publishDeskThread` — на длинных чатах O(n) на каждое событие.

## 5. Оценка UX

- **Форма ask_user не исчезает после отправки ответа** (баг 4.1) — главный UX-дефект: пользователь не понимает, принят ли ответ.
- **Нет индикации, что ран возобновился** — `resumed` не обрабатывается нигде в UI.
- **Нет кнопки Cancel/Skip на ask-карточке** — если агент задал бессмысленный вопрос, пользователь может только ответить; cancel рана доступен только через общий стоп чата.
- **Ошибка ответа молча ретраится** — шторм 409 невидим пользователю (catch пустой в `hitl-prompt.tsx:29`), чат просто «висит».
- Положительное: карточки Confirm с превью параметров тулов, radio-выбор опций, свободный текст, mark-unread — сделано хорошо.

## 6. Минимальный план доведения ReAct + ask_user до «работает идеально»

1. **Возобновляемость act-узла**: восстановить `output` из последнего assistant-сообщения (`$state.messages`) при старте сегмента с tool:call-узла (фикс Бага 1) — либо персистенция output в снапшот.
2. `await engine.recover()` + `drainQueue()` после recover (Баг 2).
3. `POST /resume` → при живом ране вернуть его runId (202), `findByThread` игнорирует finished (Баг 3, серверная часть).
4. Клиент: обработка `resumed` в `pendingHitl`, разрыв эффекта-цикла (409 → подключение к SSE, не ретрай), backoff (Баг 3, клиентская часть).
5. Явные ошибки вместо молчаливых no-op в `apply()`/`drainQueue()` (Баг 4).
6. Синтетический tool-result при reject (P1.2) и дедуп `ask` при recover (P1.3).

Пункты 1–5 закрывают оба ваших симптома (шторм + «проглоченный» respond) и делают ask_user полностью рабочим для ReAct-агента.
