# Spawn: dead child HITL + strict target resolution — баг-репорты

Дата: 2026-09-08. Источник: два скриншота стенда + `~/.harnesys/studio.db` (тред `934ffccb`, старый тред `a2ff6b79`) + чтение кода. Без фиксов, только факты.

## BUG-1: вопрос прав ребёнка нельзя подтвердить — «run not found» (critical)

Симптом: карточка «Allow List Dir?» в родительском треде; кнопка Allow → тост «Could not allow — run not found»; в network-панели три красных `respond`.

Доказательства:
- В `runs` ровно одна строка — родительский ран (`dd0ab2b9`, статус cancelled). Строк для спавнов нет вообще: дети живут вне lifecycle.
- В `run_events` треда три `ask` под spawn-runId (`571e0962|19`, `4c7d57fb|23`, `1c6bf9a5|33`, все `source: permission`, `askId: perm/…`). Ни одного `hitl.answer` к ним.
- `respond-run.use-case.ts:41-44`: `lifecycle.get(runId)` → null → `NotFoundError('run not found')` → 404 (`http.error.ts:29-30`).
- Клиент шлёт чужой runId: `hitl-actions.ts:5-11` везёт только `threadId + askId`; `run-stream-client.ts:121-134` подставляет `currentRunId` = родительский ран. То есть POST идёт с askId ребёнка на ран родителя — мимо дважды.
- `pending-hitl.ts:20-37` выбирает newest `ask` по всему логу без оглядки на `runId`; `PendingHitl` (`:3-9`) поля runId не имеет. Карточка ребёнка неотличима от карточки родителя.
- Контрольный случай: родительский ask (`dd0ab2b9|135`) получил `hitl.answer` (`|136`) — механизм для корневых ранов исправен.

Корень: дочерние раны — граждане второго сорта: ни строки в `runs`, ни lease, ни HITL-проводки. Их вопросы при этом показываются в UI родителя как отвечаемые.

## BUG-2: ребёнок, запросивший ввод, умирает с needs_input (major)

Симптом: все три спавна в треде завершились `agent.failed`, карточки «Explorer · failed».

Доказательства (БД, тот же тред):
- `agent.failed` идёт сразу за `agent.spawned` (пары seq 162/163, 265/266, 369/370, один timestamp): `code: needs_input`, `message: spawn child ended with status needs_input`.
- `graph-spawn.ts:166-184`: статус снапшота ребёнка `needs_input` маппится в `error` результата; отдельная ветка под `AskUserInterrupt` в `runOneChild` (`:149-165`) отсутствует. Родитель не встаёт на паузу никогда.

Корень: тот же, что BUG-1. Некуда ставить на паузу и некому отвечать: у ребёнка нет lifecycle-записи, resume некуда писать.

## BUG-3: резолв цели спавна — только точное совпадение (robustness)

Симптом (скрин 1): `spawn target "c5fc6a-8378-…" not found`, красный Error, ран убит.

Доказательства:
- В треде `a2ff6b79` tool-события несут `agentId: c5fc6a-8378…`, а в каталоге `Explorer = c5fcde6a-…`. Модель выронила `de` из UUID.
- `resolveTargets` (`graph-spawn.ts:101-111`): `agents.resolve` → undefined → `spawn_target_missing`. Резолв — только `findById` (`workspace-harnesys.registry.ts:136-143`); порт `AgentsResolve` (`create-runtime.ts:26-28`) — один метод без поиска.
- `agents_spawn` execute (`create-agents-tools.ts:136-142`) проверяет только форму `calls`, id не валидирует — ошибка всплывает поздно, уже в графе, с текстом без списка доступных агентов (модели не за что зацепиться для самокоррекции).

Корень: контракт «модель всегда отдаёт байт-в-байт UUID» против известного поведения моделей. Строгий резолв без fallback и без fail-fast с подсказкой.

## BUG-4: висячая ask-карточка после смерти ребёнка (minor, UX)

Симптом: после `agent.failed` карточка «Allow …?» остаётся в ленте; Allow гарантированно 404 (BUG-1).

Доказательства: `pendingHitl` не знает статуса рана-владельца ask; ask ребёнка остаётся newest-ask лога, карточка рендерится (`hitl-prompt.tsx:18-28`, гейт только на `activeRuns[thread.id]`).

Корень: следствие BUG-1/BUG-2. Отдельным фиксом не чинить — уйдёт вместе с ними.

## Общий корень (то самое «изначально не так»)

Дочерние раны обходят run lifecycle целиком: нет строки в `runs`, нет lease/epoch, нет resume-пути, нет ask-паузы. При этом их события, вопросы и ошибки показываются в UI родителя как полноправные. Половина системы (журнал/SSE/карточки — наши Tasks 1-14) считает детей видимыми, вторая половина (lifecycle/HITL) — несуществующими. Отсюда все четыре бага.

## Резолюция (согласована в чате)

Вариант A (полноправные раны) отвергнут хозяином: сабагент никогда не должен ничего уточнять — задача родителя ставить задачу без вопросов. Принят вариант B, глубокий:

- Песочница: в дочернем контексте не спрашивает ни один из четырёх источников (permission-gate, approve-gate, ask_user-тул, control:interrupt-узел). Семантика: deny-и-продолжить — заблокированный тул даёт error-результат с объяснением, ребёнок доделывает остальное.
- Deny пишется в журнал ребёнка и в `state.$deniedTools` (параллельно `recordGranted`); итог ребёнка несёт `blocked: [{tool, reason}]`, видно в Spawn results.
- Родитель судит о fit'е заранее: `agents_list` отдаёт tools + model; описания `agents_spawn`/`agents_list` фиксируют one-shot контракт; `agents_spawn` валидирует цели fail-fast (exact → префикс → имя, со списком агентов в ошибке) — заодно чинит BUG-3.
- Хвосты: `pendingHitl` игнорирует ask из spawn-runId (старые журналы).

## Направления починки (без кода, на решение)

A. Дети — полноправные раны: строка в `runs` с `parentRunId`, lease у родителя (или делегированный), ask ребёнка ставит на паузу цепочку и приходит пользователю с пометкой «спрашивает сабагент N»; ответ пишется в журнал ребёнка, resume — по его runId. Клиент везёт runId ask'а.
B. Дети — песочница one-shot: permission-gated инструменты в дочернем контексте не спрашивают, а получают детерминированный вердикт (deny с объяснением в результат спавна). Вопросов назад нет по построению; ask-карточки детей в родителе не показываются вовсе.
C. BUG-3 отдельно и в любом случае: префикс/имя-резолв + fail-fast в `agents_spawn` со списком агентов в ошибке.
